# ROUND 6 — the brief

You are a **fresh agent**. You have no context from any previous round,
no memory of this repository, and nobody to ask. Everything you need is
here and in the tools.

## The brief

> **A fantasy village with a farmer, a slime enemy, 4 pickups and a 3-tile
> ground. Produce a playable 1-screen game including its art, using only
> the repo tools.**

## What you may read

* `AGENTS.md` — the map (read it first; it says what the documents are for).
* The art documents: `art/README.md`, `art/CRITIQUE.md`,
  `art/STYLE_TEMPLATE.md`, `docs/art/PROVENANCE.md`, `docs/art/INGEST.md`.
* The tool's own help: `tools/arc1-art --help`, `tools/arc1-art <cmd> --help`,
  `python3 tools/arc1_assetc.py --help`, `build/arcade1 --help`,
  and the source of the tools you use.
* The guest SDK headers: `programs/arcade1.h`, `programs/gfx.h`,
  `programs/asset.h`, `programs/text.h`.
* The example guests: `programs/example_*.c`, and the one end-to-end
  asset example the documentation points at,
  `programs/experimental/asset_demo.c` (GAME_DEV_GUIDE.md calls it "a
  working end-to-end example" — the documentation and this brief must not
  contradict each other).

**Do not read** the other games' source (`programs/petalblade*.c`, the rest
of `programs/experimental/`), the other rounds' art (`round3/`, `round4/`,
`round5/`), or the roadmaps. The point of this round is to find out what
the *documentation* is missing — if you read a finished example, you will
not find that out.

## What you must produce

1. **A playable one-screen game** in `round6/`:
   * `round6/game.c` — the guest (freestanding C for RV32IM, no libc);
   * `round6/assets.json` — the manifest (the palettes, the sprites, the
     map);
   * the generated header and the strips, built by the tools;
   * the game's image (`round6/round6.arc1`) and its golden
     (`round6/round6.golden`).
2. **A `ROUND_LOG.md`** in this folder, kept as you go (see below).

## The rules

* **The tools are the only way in.** The art is generated by
  `tools/arc1-art` (the drawing library, the `.px` pixmaps, the rig) and
  compiled by `tools/arc1_assetc.py`; the game is built and run with
  `build/arcade1` (build it with `make build/arcade1`).
* **Every generated file is regenerated by a command, never hand-edited.**
  If you edit a generated file, that is a failure — say so in the log.
* **Determinism.** The same inputs must give the same bytes.
* **The golden is the regression.** Lock the game with the CLI's own
  `golden` command (`arcade1 golden ... --out ...`), then check it with
  `arcade1 test ... --golden ...`.
* **Every asset must pass `arc1-art check`** (the visual checks) — and
  the review in `art/CRITIQUE.md` is how you judge what the checks cannot.
* If the documentation is wrong, incomplete or missing, **that is a
  finding**: write it down and work around it. Do not fix the docs
  yourself; the round is about the docs, not about them.

## The log

Keep `ROUND_LOG.md` in this folder and add to it **as you go** (not at the
end). It must record:

* every attempt, in order, with what you tried and what happened;
* every **DOC GAP** — a place where the documentation did not tell you
  what to do, or told you the wrong thing. Quote the sentence that
  failed you. This is the most valuable thing in the log;
* the **time to the first compliant asset** (a strip that passes
  `arc1-art check` and is committed to the manifest);
* anything you had to figure out by reading the tool's source.

At the end, the log must also say: what you built, how it plays (the
controls, the win/lose condition), and where the art is weakest.

## Done means

* the game builds, runs and is playable (a scripted session reaches the
  end state);
* it is golden-locked with the CLI's `golden` command and the golden
  passes with `arcade1 test --golden`;
* every asset passes `arc1-art check`;
* no generated file was hand-edited;
* `ROUND_LOG.md` is complete.
